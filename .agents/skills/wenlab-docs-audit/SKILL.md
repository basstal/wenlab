# wenlab 文档审计

对目录、单个 Markdown 文件或 Git 项目做文档质量审计，分为三层：

| 层次     | 解决的问题                                           | 手段                                  |
| -------- | ---------------------------------------------------- | ------------------------------------- |
| 格式质量 | Markdown 结构、中文排版、拼写、术语与链接是否合规    | wenlab Node.js Gate（默认 LocalGate） |
| 内容质量 | 事实是否准确，信息是否完整，是否存在过期表述         | Agent 语义审校                        |
| 编辑质量 | 文章是否连贯、简洁、自然，能否满足特定读者的阅读需求 | 以目标读者视角通读全文复审            |

## 1. 确定审计模式

| 用户要求                     | 执行内容                                   |
| ---------------------------- | ------------------------------------------ |
| 未限定层次（默认）           | 格式质量 + 内容质量 + 编辑质量             |
| 明确只审计格式质量           | 只运行格式质量脚本，汇报报告的绝对路径     |
| 明确只审计内容质量或编辑质量 | 只做对应层次的 Agent 语义审校，不运行 Gate |

审计范围由用户给出的目录、文件或 Git 项目决定；未给出时询问用户，不默认整个磁盘或主目录。

## 2. 获取审计上下文

先运行只读的上下文脚本，得到项目根目录、文件清单、项目类型和适用规范。下文的 `<wenlab>` 是包含本 Skill 的 wenlab 仓库绝对路径：

```text
node "<本 skill 目录>/scripts/Get-AuditContext.mjs" -Path "<审计范围的绝对路径>"
```

输出 JSON 的关键字段：

- `ProjectRoot`：Git 仓库根目录；不在 Git 中时为范围目录本身。
- `FileListRule`：`git`（范围正好是仓库根目录，按 `.gitignore` 规则收集）、`recursive`（递归收集，跳过 `.git` 和 `node_modules`）或 `file`；两种目录规则都跳过 `.wenlab/docs-audit.json` 中 `exclude` 匹配的目录或文件，以及 `<wenlab>/.tmp/docs-audit/` 下的报告。规则与 Gate 一致。
- `ProjectType`：`engineering` 或 `general`，依据是项目根目录及下两级是否有工程标志文件（如 `package.json`、`*.sln`、`*.csproj`、`go.mod`、`Cargo.toml`、`pyproject.toml`、Unity 的 `ProjectVersion.txt`），见 `ProjectEvidence`。
- `Specifications`：本次语义审校适用的规范文件。
- `QualityLayers`：质量分层与文章类型审阅重点。
- `SemanticChecklist`：中文技术写作语义审校清单，列出 Gate 无法机械检查、需逐条核对的句子、用词与标点规则。
- `ExcludePatterns`：项目级 `exclude` 规则列表。
- `MarkdownFiles`：本次审计的文档清单，相对于 `ProjectRoot`。

用户明确说明项目类型时，以用户说明为准，并在汇报中注明。

## 3. 格式质量

运行本地格式质量阀门 LocalGate，并指定唯一的报告目录，以便无论通过与否都能定位报告：

```text
node "<本 skill 目录>/scripts/Get-AuditContext.mjs" -Path "<审计范围的绝对路径>"
node "<wenlab>/tools/docs-audit/LocalGate.mjs" -Path "<审计范围的绝对路径>" -ReportDirectory "<wenlab>/.tmp/docs-audit/skill/<yyyyMMddTHHmmss>"
```

第二条命令的报告目录使用当前时间生成唯一值；在该目录下递归定位 `diagnosis.md`，并汇报其绝对路径。

- 用户要求检查外部网址时改用远程格式质量阀门 `RemoteGate.mjs`，它会访问网络。
- 退出码 0 为通过，1 为文档质量问题，2 为缺工具、版本不符或配置故障。退出码为 2 且提示缺工具时，报告工具名、所需版本和错误信息后停止格式审计，不安装、不换来源。
- 汇报 `diagnosis.md` 的绝对路径、各检查的 PASS/FAIL 状态和退出码。
- 汇报 `diagnosis.md` 的“对归档文档的链接引用”一节：列出链接时，逐条汇报其中的文件、行列和链接目标；写明没有这类链接时，汇报没有指向归档文档的链接；没有这一节时，说明检查在扫描链接前已中止。这一节不影响退出码，也不需要判断引用是否合理。只审计格式质量时，到此结束。
- 项目词典放在 `<项目根目录>/.wenlab/dictionary.txt`，规则覆盖与排除列表放在 `<项目根目录>/.wenlab/docs-audit.json`，详见 `<wenlab>/docs/Markdown-审计入口.md`。

## 4. 内容质量与编辑质量

### 4.1 选择规范

- `ProjectType` 为 `general`（不是工程项目）：使用 `<wenlab>/docs/通用写作规范.md`。
- `ProjectType` 为 `engineering`（工程项目）：使用 `<wenlab>/docs/当前状态文档写作规范.md`，它以通用写作规范为基准，两份都要读。
- 两种情况都读 `<wenlab>/docs/agent写作备忘.md`，按文章类型确定审阅重点。
- 审阅编程、计算机、游戏技术等中文技术类文档时，另对照 `SemanticChecklist`（`<wenlab>/docs/中文技术写作语义审校清单.md`）逐条核对编辑质量。

审校前完整阅读选定的规范，以规范原文为准，不凭记忆概括。

### 4.2 逐篇审校

项目 `exclude` 命中的目录或文件不纳入内容质量与编辑质量审校，跨文档比较也不计入这些文档；`MarkdownFiles` 已按此排除。未在配置中排除时，其中的文档照常审校。用户直接把被排除的目录或其中的文件指定为审计范围时，也照常审校。

对 `MarkdownFiles` 中的每一篇，完整阅读全文后检查：

- 四个核心：frontmatter 是否写明“读者”“用途”“内容核心范围”“不涉及的范围”，正文是否服务于读者和用途、覆盖核心范围且不越界。Agent 专用或对 frontmatter 格式有固定要求的文档（如 SKILL.md、AGENTS.md）按通用写作规范可不写四个核心，不作为问题报告。
- 内容质量（用户只要求编辑质量时跳过）：
  - 事实是否准确：命令、路径、参数、版本、配置等可核验的说法，到项目中的代码、配置或其他证据处逐项核对。
  - 信息是否完整：是否缺少必要前提、限定条件或例外。
  - 是否过期：失效表述、修订痕迹（如“不再”“仍”“原来”）、未标注的历史信息；工程项目按当前状态文档规范处理。
  - 是否区分事实、推断、假设、建议和个人观点。
- 编辑质量（用户只要求内容质量时跳过）：段落是否围绕单一主旨、承接与指代是否清楚、术语是否一致、有无空话套话和重复论证、结构是否便于目标读者查阅。
- 跨文档：同一事实在不同文档中是否矛盾，疑似重复是否损害或有助于各文档的独立阅读。

文档较多时可分批审校，但必须覆盖清单中的全部文档；未审校的文档要在汇报中列出，不得默认视为通过。

### 4.3 汇报格式

- 适用规范及原因（项目类型与依据）。
- 按文档和层次列出问题，每条写明位置（文件与行号）、问题、依据的规范条目和修改建议；没有问题的文档单独列出。
- 内容质量与编辑质量分开汇报；默认模式下再附格式质量报告的绝对路径和状态。

## 约束

- 审计只读，不修改被审计的文档；用户要求修复时，按适用规范修订，涉及 frontmatter 四个核心的修改先经用户确认。
- 不安装、升级或下载任何依赖；Gate 缺工具时按第 3 节报告并停止。
- 一次性脚本和临时文件写到 `<wenlab>/.tmp/` 下。
- Gate 通过不代表语义审校完成；语义审校的结论需附可核验的位置，不以文本相似度代替语义判断。
